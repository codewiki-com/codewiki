## 什么是 ADR？

**架构决策记录（Architecture Decision Record，ADR）**是一种文档，用于记录重要的架构决策及其背景和影响。ADR 是一种轻量级但强大的方式，用于记录软件项目中架构选择背后的"为什么"。

### 为什么需要 ADR？

在软件开发中，团队经常面临以下挑战：

1. **知识流失**：几个月前做出的关键决策被遗忘，其背后的理由也随之消失
2. **新人入职困难**：新团队成员难以理解系统为何以某种方式构建
3. **重复讨论**：因为之前的决策没有记录，同样的架构讨论反复发生
4. **背景丢失**：当最初的决策者离开时，关键的背景信息也随之消失
5. **技术债务困惑**：团队不记得为何做出某些权衡

ADR 通过以下方式解决这些问题：

- **历史背景**：记录决定了什么以及为什么
- **组织记忆**：知识超越个人团队成员而延续
- **决策透明**：每个人都能理解选择背后的理由
- **变更追踪**：架构思维随时间演进的记录
- **责任明确**：决策有明确的负责人

### ADR 的起源

ADR 的概念由 Michael Nygard 在其 2011 年的博客文章"Documenting Architecture Decisions"中普及。此后，ADR 已成为软件工程中广泛采用的实践，尤其在敏捷和 DevOps 环境中。

## ADR 结构

一个结构良好的 ADR 包含几个关键部分。让我们详细了解每个组成部分。

### 基本 ADR 模板

```markdown
# ADR-{编号}: {标题}

## 状态

{提议中 | 已接受 | 已弃用 | 被 ADR-XXX 取代}

## 背景

{描述情况和需要解决的问题}

## 决策

{陈述所做的决策}

## 影响

{描述应用决策后产生的结果}
```

### 标题

标题应简短、描述性强且面向行动。它应清楚地表明正在做出什么决策。

**好的标题：**
- "使用 PostgreSQL 作为主数据库"
- "采用微服务架构"
- "实现 JWT 身份验证"
- "选择 React 作为前端框架"

**不好的标题：**
- "数据库决策"
- "架构相关"
- "前端"

### 状态

状态字段追踪决策的生命周期：

| 状态 | 描述 |
|--------|-------------|
| **提议中** | 决策正在讨论中，尚未最终确定 |
| **已接受** | 决策已达成一致并生效 |
| **已弃用** | 决策不再相关，但保留作为历史参考 |
| **已取代** | 决策已被更新的 ADR 替代 |

```markdown
## 状态

已接受

被 [ADR-0015](./adr-0015-migrate-to-mongodb.zh.md) 取代
```

### 背景

背景部分描述影响因素，包括技术、政治、社会和项目特定的约束。这可以说是最重要的部分，因为它捕获了决策背后的"为什么"。

**应包含的内容：**
- 当前情况和痛点
- 驱动决策的业务需求
- 技术约束和限制
- 团队技能和经验
- 时间和预算约束
- 利益相关者的关注点

```markdown
## 背景

我们的电商平台正在经历显著增长，过去一年流量增加了 300%。
当前的单体架构正在承受压力：

- 部署需要 45 分钟并要求完全重启应用
- 支付模块的一个 bug 最近导致整个系统宕机
- 开发团队已增长到 15 名工程师，导致频繁的合并冲突
- 系统的不同部分有截然不同的扩展需求（产品目录 vs. 结账）

我们需要决定一种架构方法来支持：
- 系统组件的独立部署
- 关键服务之间的故障隔离
- 团队自治和并行开发
- 单个组件的成本效益扩展
```

### 决策

决策部分清楚地陈述已做出的决定。它应该直接且明确。包括所选方案并简要说明为何选择它而非其他替代方案。

```markdown
## 决策

我们将为电商平台采用微服务架构，首先将以下限界上下文提取为独立服务：

1. **产品目录服务**：处理产品信息、分类和搜索
2. **订单服务**：管理订单生命周期和履行
3. **支付服务**：处理支付和退款
4. **用户服务**：管理用户账户和身份验证

我们选择微服务而非继续使用单体架构，因为：
- 允许高流量服务（目录）独立扩展
- 团队可以独立部署各自的服务
- 一个服务的故障不会导致整个平台宕机
- 不同的服务可以使用适当的技术栈

我们考虑但拒绝了：
- **模块化单体**：虽然更简单，但不能解决我们的扩展和故障隔离需求
- **Serverless**：我们长时间运行的支付流程不适合 serverless 模型
```

### 影响

影响部分描述应用决策后产生的结果。要诚实地说明正面和负面的结果。

```markdown
## 影响

### 正面

- **独立可部署性**：团队可以在不与他人协调的情况下部署服务
- **技术灵活性**：服务可以使用最合适的技术栈
- **故障隔离**：故障被限制在服务边界内
- **可扩展性**：单个服务可以根据需求进行扩展
- **团队自治**：清晰的所有权边界减少冲突

### 负面

- **复杂性增加**：分布式系统本质上更难构建和运维
- **网络延迟**：服务间通信增加延迟
- **数据一致性**：跨服务维护一致性需要仔细设计
- **运维开销**：更多服务意味着更多部署、监控和基础设施需要管理
- **测试复杂性**：跨服务的集成测试更具挑战性

### 中性

- 我们需要投资服务网格技术（Istio 或 Linkerd）
- 团队结构需要与服务边界对齐
- 我们需要建立 API 版本控制和弃用策略
```

## 扩展 ADR 部分

许多团队扩展基本 ADR 模板，增加额外部分以捕获更多背景信息。

### 考虑的选项

记录评估过的替代方案：

```markdown
## 考虑的选项

### 选项 1：继续使用单体（维持现状）
- **优点**：无需迁移工作，团队熟悉代码库
- **缺点**：不能解决扩展或故障隔离问题
- **预估工作量**：无

### 选项 2：模块化单体
- **优点**：改善代码组织，比微服务复杂度低
- **缺点**：仍需完整部署，故障隔离有限
- **预估工作量**：3 个月

### 选项 3：微服务架构（选中）
- **优点**：独立扩展，故障隔离，团队自治
- **缺点**：运维复杂度更高，分布式系统挑战
- **预估工作量**：初始提取 6-9 个月

### 选项 4：Serverless 架构
- **优点**：无需服务器管理，自动扩展
- **缺点**：冷启动，供应商锁定，不适合长时间运行的流程
- **预估工作量**：9-12 个月
```

### 参与者

记录参与决策的人员：

```markdown
## 参与者

- **决策者**：Jane Smith（CTO），John Doe（首席架构师）
- **咨询对象**：后端团队，DevOps 团队，产品管理
- **知会对象**：所有工程团队，高管层
```

### 相关决策

链接到相关的 ADR 以提供背景：

```markdown
## 相关决策

- [ADR-0003: 使用 Kubernetes 进行容器编排](./adr-0003.md)
- [ADR-0007: 实现 API 网关模式](./adr-0007.md)
- [ADR-0012: 采用事件驱动通信](./adr-0012.md)
```

### 备注和参考资料

包含支持材料：

```markdown
## 备注

- 2024 年第二季度完成概念验证，目录服务延迟改善 40%
- 分布式系统模式培训计划安排在第三季度

## 参考资料

- [Building Microservices by Sam Newman](https://samnewman.io/books/building_microservices/)
- [内部性能分析报告 (Confluence)](https://wiki.example.com/perf-analysis)
- [AWS 微服务最佳实践](https://aws.amazon.com/microservices/)
```

## 何时编写 ADR

并非每个决策都需要 ADR。以下是何时创建 ADR 的指南：

### 需要编写 ADR 的情况

1. **决策重大**：影响系统整体结构或关键质量属性
2. **决策难以更改**：撤销需要大量工作
3. **决策有争议**：存在多个有效选项且各有权衡
4. **决策影响多个团队**：其他团队需要理解或遵循该决策
5. **决策涉及外部依赖**：选择供应商、框架或服务
6. **曾经讨论过**：如果同样的讨论反复出现，记录下决策

### 值得记录为 ADR 的决策示例

```
架构模式：
- 采用微服务 vs. 单体
- 选择事件驱动 vs. 请求-响应通信
- 实现 CQRS 或 Event Sourcing

技术选择：
- 选择数据库（PostgreSQL vs. MongoDB vs. DynamoDB）
- 选择前端框架（React vs. Vue vs. Angular）
- 选择消息代理（Kafka vs. RabbitMQ vs. SQS）

开发实践：
- API 设计标准（REST vs. GraphQL vs. gRPC）
- 测试策略（单元测试 vs. 集成测试 vs. 契约测试）
- 部署方式（蓝绿部署 vs. 金丝雀发布 vs. 滚动更新）

安全决策：
- 身份验证机制（JWT vs. sessions vs. OAuth）
- 数据加密策略
- 访问控制模型（RBAC vs. ABAC）
```

### 不需要编写 ADR 的情况

- 决策琐碎或容易撤销
- 是团队特定的实现细节
- 是临时的变通方案（改用技术债务工单）
- 标准最佳实践已经适用

## ADR 模板

### 简化模板

用于较简单的决策：

```markdown
# ADR-{编号}: {标题}

**日期**: {YYYY-MM-DD}
**状态**: {提议中 | 已接受 | 已弃用 | 已取代}

## 背景

{是什么问题促使我们做出这个决策？}

## 决策

{我们提议和/或正在做的改变是什么？}

## 影响

{这个改变使什么变得更容易或更困难？}
```

### 完整模板

用于需要更多细节的复杂决策：

```markdown
# ADR-{编号}: {标题}

**日期**: {YYYY-MM-DD}
**状态**: {提议中 | 已接受 | 已弃用 | 已取代}
**决策者**: {参与人员列表}
**技术故事**: {工单或问题的链接}

## 背景和问题陈述

{描述背景和问题陈述，例如用两到三句话自由描述。
你可能想以问题的形式阐述问题。}

## 决策驱动因素

- {驱动因素 1，例如一种力量、面临的关注点...}
- {驱动因素 2，例如一种力量、面临的关注点...}
- ...

## 考虑的选项

1. {选项 1}
2. {选项 2}
3. {选项 3}
...

## 决策结果

**选择的选项**: "{选项 X}"，因为 {理由}。

### 正面影响

- {例如，质量属性满意度的提升、需要的后续决策...}
- ...

### 负面影响

- {例如，质量属性的妥协、需要的后续决策...}
- ...

## 各选项的优缺点

### {选项 1}

{示例 | 描述 | 更多信息的指针 | ...}

- 好，因为 {论点 a}
- 好，因为 {论点 b}
- 坏，因为 {论点 c}
- ...

### {选项 2}

{示例 | 描述 | 更多信息的指针 | ...}

- 好，因为 {论点 a}
- 好，因为 {论点 b}
- 坏，因为 {论点 c}
- ...

## 链接

- {链接类型} {ADR 链接}
- ...
```

### Y-陈述模板

一种专注于影响因素的简洁格式：

```markdown
# ADR-{编号}: {标题}

**日期**: {YYYY-MM-DD}

## 决策

在 {用例/用户故事} 的背景下，
面对 {关注点}
我们决定选择 {选项}
而非 {其他选项}
以实现 {质量/目标}，
接受 {缺点/后果}。
```

## 管理 ADR

### 组织 ADR 文件

ADR 组织的常见结构：

```
docs/
└── architecture/
    └── decisions/
        ├── README.md           # 索引和概述
        ├── adr-0001-record-architecture-decisions.md
        ├── adr-0002-use-postgresql-database.md
        ├── adr-0003-adopt-microservices.md
        ├── adr-0004-implement-event-sourcing.md
        └── templates/
            ├── adr-template-minimal.md
            └── adr-template-comprehensive.md
```

### 编号规范

使用带前导零的顺序编号：

```
adr-0001-title.md
adr-0002-title.md
...
adr-0042-title.md
```

这确保在文件系统中正确排序，并便于引用特定的 ADR。

### 创建 ADR 索引

维护一个 README.md 作为索引：

```markdown
# 架构决策记录

此目录包含项目的架构决策记录（ADR）。

## 索引

| ADR | 标题 | 状态 | 日期 |
|-----|-------|--------|------|
| [0001](./adr-0001-record-architecture-decisions.md) | 记录架构决策 | 已接受 | 2024-01-01 |
| [0002](./adr-0002-use-postgresql-database.zh.md) | 使用 PostgreSQL 作为主数据库 | 已接受 | 2024-01-05 |
| [0003](./adr-0003-adopt-microservices.md) | 采用微服务架构 | 已接受 | 2024-01-15 |
| [0004](./adr-0004-use-kafka-messaging.md) | 使用 Kafka 进行事件流处理 | 提议中 | 2024-01-20 |

## 已取代的决策

| ADR | 标题 | 被取代者 |
|-----|-------|---------------|
| [0002](./adr-0002-use-postgresql-database.zh.md) | 使用 PostgreSQL | [0015](./adr-0015-migrate-to-mongodb.zh.md) |

## 创建新 ADR

请参阅 [TEMPLATE.md](./templates/adr-template.md) 获取模板。
```

### ADR 生命周期管理

```
                    ┌─────────────┐
                    │   提议中    │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │  已接受  │ │  已拒绝  │ │  已推迟  │
        └────┬─────┘ └──────────┘ └──────────┘
             │
    ┌────────┴────────┐
    │                 │
    ▼                 ▼
┌──────────┐    ┌──────────────┐
│  已弃用  │    │    已取代    │
└──────────┘    │  由 ADR-XXX  │
                └──────────────┘
```

### 更新 ADR

ADR 一旦被接受，通常应该是**不可变的**。与其修改已接受的 ADR：

1. **对于小的澄清**：添加带日期修订的"备注"部分
2. **对于重大变更**：创建一个新的 ADR 来取代旧的
3. **更新状态**：将旧 ADR 标记为"被 ADR-XXX 取代"

```markdown
## 状态

被 [ADR-0015: 迁移到 MongoDB](./adr-0015-migrate-to-mongodb.zh.md) 取代

## 修订历史

- **2024-03-15**：澄清了只读副本可用于报表查询
- **2024-06-01**：由于需求变化，此 ADR 已被取代
```

## ADR 工具

### 命令行工具

**adr-tools**（作者：Nat Pryce）：

```bash
# 安装（macOS）
brew install adr-tools

# 初始化 ADR 目录
adr init docs/architecture/decisions

# 创建新 ADR
adr new "Use PostgreSQL as Primary Database"

# 列出所有 ADR
adr list

# 生成目录
adr generate toc > docs/architecture/decisions/README.md

# 取代现有 ADR
adr new -s 2 "Migrate to MongoDB"
```

**Log4brains**：

```bash
# 安装
npm install -g log4brains

# 初始化
log4brains init

# 创建新 ADR
log4brains adr new

# 以网站形式预览 ADR
log4brains preview
```

## 完整 ADR 示例

这是一个完整的示例：

```markdown
# ADR-0007: 使用 JWT 进行 API 身份验证

**日期**: 2024-01-15
**状态**: 已接受
**决策者**: Alice Chen（安全负责人）, Bob Smith（后端负责人）,
Carol Davis（DevOps 负责人）
**技术故事**: PROJ-1234

## 背景和问题陈述

我们的 API 目前使用基于会话的身份验证，服务端会话存储在 Redis 中。
随着我们扩展到多个区域并采用微服务架构，我们面临挑战：

1. 会话存储成为单点故障
2. 跨服务身份验证需要会话共享
3. 移动客户端难以管理会话 cookie
4. 水平扩展需要粘性会话或共享会话存储

我们需要一种身份验证机制：
- 跨多个服务工作而无需共享状态
- 水平扩展无需协调
- 同时支持 Web 和移动客户端
- 保持安全最佳实践

## 决策驱动因素

- **可扩展性**：必须支持 10 倍流量增长
- **微服务兼容性**：必须跨服务边界工作
- **移动支持**：必须与原生移动应用良好配合
- **安全性**：必须满足 SOC 2 合规要求
- **开发者体验**：应易于实现和调试

## 考虑的选项

1. **继续使用会话 + Redis 集群**
2. **JWT（JSON Web Tokens）**
3. **OAuth 2.0 + 不透明令牌**
4. **API 密钥**

## 决策结果

**选择的选项**: "JWT（JSON Web Tokens）"，因为它提供无状态身份验证，
自然地跨微服务工作，同时支持 Web 和移动客户端。

### 实现细节

- 使用 RS256（非对称）签名以便更好的密钥管理
- 访问令牌 15 分钟过期
- 刷新令牌 7 天过期并存储在数据库中
- 包含最少的声明：`sub`、`email`、`roles`、`exp`、`iat`
- 实现令牌刷新端点以实现无缝续期

### 正面影响

- **无状态身份验证**：无需共享会话存储
- **服务独立**：每个服务可以独立验证令牌
- **水平扩展**：不需要粘性会话或共享状态
- **移动友好**：与 Authorization 头自然配合
- **性能**：令牌验证不需要数据库查询

### 负面影响

- **令牌撤销复杂性**：无法立即撤销 JWT
  - 缓解措施：短过期时间 + 刷新令牌撤销
- **令牌大小**：JWT 比会话 ID 大
  - 缓解措施：保持声明最小化
- **密钥管理**：需要安全的密钥轮换流程
  - 缓解措施：使用 AWS KMS 进行密钥管理

## 各选项的优缺点

### 选项 1：会话 + Redis 集群

- 好，因为对现有代码改动最小
- 好，因为可以即时撤销会话
- 坏，因为 Redis 成为关键依赖
- 坏，因为多区域设置复杂
- 坏，因为跨服务的会话共享复杂

### 选项 2：JWT（选中）

- 好，因为无状态且可扩展
- 好，因为跨服务工作无需协调
- 好，因为是行业标准，有优秀的库支持
- 坏，因为无法即时撤销令牌
- 坏，因为载荷大小较大

### 选项 3：OAuth 2.0 + 不透明令牌

- 好，因为企业级安全性
- 好，因为支持令牌撤销
- 坏，因为需要令牌内省端点
- 坏，因为复杂度更高
- 坏，因为验证有额外延迟

### 选项 4：API 密钥

- 好，因为实现简单
- 坏，因为不适合用户身份验证
- 坏，因为没有自定义逻辑就没有过期
- 坏，因为令牌中没有用户上下文
```

## 最佳实践

### 编写有效的 ADR

1. **简洁但完整**：包含足够的背景但不冗长
2. **专注于"为什么"**：推理比决策本身更重要
3. **诚实对待权衡**：记录优点和缺点
4. **使用简单语言**：避免不必要的术语
5. **包含示例**：代码片段或图表有助于澄清决策
6. **链接到证据**：引用基准测试、研究或原型

### 团队采用技巧

1. **从小处开始**：从主要决策开始，而不是每个选择
2. **使其简单**：使用模板和工具
3. **审查 ADR**：在架构讨论中包含 ADR 审查
4. **以身作则**：高级工程师应首先编写 ADR
5. **引用 ADR**：在代码审查和讨论中引用相关的 ADR
6. **表彰好的 ADR**：认可写得好的文档

### 常见陷阱及避免方法

| 陷阱 | 解决方案 |
|---------|----------|
| 事后编写 ADR | 将 ADR 作为决策过程的一部分创建 |
| 细节过多 | 专注于架构重要性，而非实现 |
| 不更新状态 | 每季度审查 ADR 状态 |
| ADR 孤立存在 | 将相关的 ADR 链接在一起 |
| 忽视影响 | 诚实对待负面结果 |
| 无审查流程 | 在架构治理中包含 ADR 审查 |

## 总结

架构决策记录是一种简单但强大的工具，用于捕获重要架构选择背后的推理。通过记录决策及其背景和影响，团队可以：

- **保存组织知识**，超越个人贡献者
- **加速新人入职**
- **防止重复讨论**已确定的决策
- **追踪架构演进**
- **通过结构化思考提高决策质量**

记住关键原则：

1. 专注于**重大的、难以撤销的**决策
2. 记录**背景和推理**，而不仅是选择
3. **诚实对待权衡**和影响
4. ADR 一旦接受就保持**不可变**
5. 使 ADR **易于发现**且组织良好

ADR 在成为团队工作流程的自然部分时效果最好，而不是事后补救。从几个重要决策开始，建立模板和规范，逐步建立宝贵的架构知识档案。
