## 什么是闭包

闭包（closure）是一个函数，它还能访问定义位置对应的词法环境中的绑定。在 Python 中，它通常是由外层函数返回的内层函数。外层调用可以结束，但内层函数需要的绑定仍然可用。

函数内使用、却在函数外绑定的名称叫作<Term id="free-variable">自由变量（free variable）</Term>。提供该绑定的函数作用域叫作<Term id="enclosing-scope">外层作用域（enclosing scope）</Term>。函数代码与这些保留下来的绑定共同构成闭包。

Python 支持闭包，是因为函数像其他对象一样传递时，词法作用域仍应有效。如果没有这条规则，返回嵌套函数时就会丢掉解释其自由名称所需的上下文。闭包可以携带配置或私有状态，无需把它们暴露为模块全局变量。装饰器、回调工厂、事件处理器、验证器，以及传给 `sorted()` 等 API 的函数中都会出现闭包。

并非每个嵌套函数都是闭包。如果内层函数只使用参数、局部名称和全局名称，就没有需要保留的外层函数绑定。

## 名称捕获的工作方式

Python 按词法规则解析名称：函数在源代码中的嵌套关系决定由哪个作用域提供名称。编译器发现内层函数引用了外层函数绑定的名称时，会为该绑定安排共享存储。

每次调用外层函数，都会为本次调用创建相应的绑定。创建内层函数时，它会与这个绑定建立连接。返回内层函数时，并不会从绑定中复制一份当前对象。保留下来的是访问绑定本身的路径。这个区别既成就了有状态闭包，也造成了延迟绑定陷阱。

它的生命周期如下：

1. 调用外层函数，创建其局部绑定。
2. 创建内层函数，并捕获它所使用的自由绑定。
3. 外层调用返回，但捕获的绑定仍可通过内层函数访问。
4. 之后调用内层函数时，它会读取或更新同一批绑定。

闭包只读取捕获的绑定时，普通的名称查找已经足够。赋值则需要额外声明，因为只要函数中出现对某个名称的赋值，该名称默认就是此函数的局部名称。`nonlocal` 告诉 Python：这次赋值针对最近外层函数作用域中已有的绑定。它既不创建新绑定，也不指向模块全局变量。

## 用闭包保存计数状态

每次调用 `make_counter()` 都会创建新的 `count` 绑定。返回的 `tick` 函数读取并重新绑定它。

<Depth level="quick">

```python run title="make_counter.py"
def make_counter():
    count = 0

    def tick():
        nonlocal count
        count += 1
        return count

    return tick


tick = make_counter()
print(tick(), tick(), tick())
print(tick.__closure__[0].cell_contents)

fresh_tick = make_counter()
print(fresh_tick())
```

```text
1 2 3
3
1
```

<TryToBreak items={['空列表', '负数计数']} />

</Depth>

第一行连续调用同一个闭包三次，因此共享的 `count` 绑定从 `0` 增加到 `3`。第二行通过函数的 `__closure__` 元组检查该绑定，看到的也是 `3`。按索引访问 `__closure__` 适合学习和诊断，但应用逻辑不应依赖 cell 的位置。

最后一行来自第二次外层函数调用。结果从 `1` 开始，因为 `fresh_tick` 捕获的是另一个 `count` 绑定。两个函数共享代码行为，不共享状态。

这种模式为状态提供了狭窄的接口：调用者可以推进计数，却不能直接给 `count` 赋值。这里的私有性只是作用域形成的约定，不是访问控制边界。持有该函数的代码仍能像示例一样检查其闭包。

## 用闭包配置函数

闭包不一定包含可变状态。它也可以保留每次后续调用都要使用的配置。

```python run title="currency_converter.py"
def make_converter(rate):
    def convert(amount):
        return amount * rate

    return convert


eur_to_usd = make_converter(1.17)
gbp_to_usd = make_converter(1.34)

print(f"{eur_to_usd(20):.2f}")
print(f"{gbp_to_usd(20):.2f}")
```

```text
23.40
26.80
```

这里的 `rate` 只被读取，没有重新绑定，因此不需要 `nonlocal`。两个转换函数仍分别拥有独立的绑定，因为它们来自对 `make_converter()` 的两次调用。返回的函数具有相同的调用形式，却带有不同的配置。

当 API 要求传入一个函数，而你希望只配置一次时，这种做法很合适。如果状态需要多种操作、验证或明确的公开表示，小型可调用类可能更清楚。如果行为天然只有一种操作，而且捕获的上下文容易命名，就可以使用闭包。

## 延迟绑定陷阱

<Term id="late-binding">延迟绑定（late binding）</Term>是指闭包运行时才查找自由名称，而不是创建函数对象时就确定其值。多个闭包共享同一个绑定，而该绑定在调用前又发生变化时，这条规则尤其重要。

> [!PITFALL]
> 在循环中创建函数，并不会自动保存本轮循环变量的值。所有函数可能捕获同一个循环绑定。

下面这个经典示例返回三个读取函数，却在循环结束后才调用它们。

```python run title="late_binding.py"
def make_readers():
    readers = []

    for index in range(3):
        # 每个 lambda 都捕获同一个循环绑定。
        readers.append(lambda: index)

    return readers


readers = make_readers()
values = [read() for read in readers]
print(values)
```

```text
[2, 2, 2]
```

循环把 `0`、`1` 和 `2` 依次赋给同一个局部名称 `index`。三个 lambda 共享它的 cell。调用它们时，循环已经让 `index` 绑定到 `2`。所以，三次调用查找到的都是同一个当前值。

**修复方法：** 创建每个函数时就绑定当前值。默认参数在创建函数时求值，因此可以让每个 lambda 都有独立的参数值。

```python run title="bound_callbacks.py"
def make_readers():
    readers = []

    for index in range(3):
        # 默认参数会固定本轮迭代的值。
        readers.append(lambda index=index: index)

    return readers


readers = make_readers()
values = [read() for read in readers]
print(values)
```

```text
[0, 1, 2]
```

`index=index` 中的同一名称承担了两个不同角色。右侧的 `index` 在创建 lambda 时从循环作用域读取。左侧的 `index` 是 lambda 之后被调用时使用的局部参数。

如果已有命名函数，只想预先绑定部分参数，`functools.partial()` 是另一种明确的修复方法。它不需要再套一层 lambda，但创建的是偏函数对象，而不是捕获这些参数的闭包。

### 重新绑定时遗漏 `nonlocal`

> [!PITFALL]
> 读取外层名称会自动按作用域查找，但在内层函数中给它赋值，会让它在整个内层函数中成为局部名称，除非使用 `nonlocal` 声明。

`count += 1` 这样的内层语句既读取 `count`，也给它赋值。如果没有 `nonlocal count`，Python 会把 `count` 当作局部名称，而读取发生时这个局部名称还没有值。调用随后会抛出 `UnboundLocalError`。

**修复方法：** 确实需要共享外层状态时，在内层函数开头附近写出 `nonlocal count`。只有当绑定确实属于模块时才使用 `global`；它并不表示“这个函数外部”。如果状态变化不容易看清，可以返回新值，或者改用带有明确方法的对象。

### 意外共享同一个闭包

> [!PITFALL]
> 在多个位置注册同一个有状态闭包，会让所有调用者操作同一个捕获的绑定。

把 `tick` 赋给另一个名称不会克隆它的 cell。把同一个 `tick` 对象添加到两个处理器列表，也不会让两个列表各自拥有独立计数器。

**修复方法：** 每个独立使用方都调用一次工厂函数，并按交错顺序测试这些使用方。如果本来就要共享状态，工厂或变量的名称应明确表达所有权。例如，`shared_request_counter` 就比 `callback` 传达了更多信息。

### 捕获生命周期更长的对象

> [!PITFALL]
> 只要闭包仍然存活，它捕获的对象就仍然可达，服务、缓存或请求对象的保留时间可能因此超过实际需要。

闭包不会引用外层函数的整个帧。只有其代码实际使用的绑定才会成为自由变量，但一个捕获的绑定本身可能指向庞大的对象图。

**修复方法：** 只捕获函数所需的小型不可变值，不要捕获仅用于取得该值的宽泛上下文对象。长期存在的回调不再需要时，应解除注册。文件、套接字或事务的生命周期必须明确时，应使用上下文管理器。

### 依赖闭包元组的位置

> [!PITFALL]
> `function.__closure__[0]` 并不是有含义的名称。增加或删除自由变量后，占据该位置的 cell 可能改变。

计数器示例能够使用零号索引，只是因为它唯一的自由变量是 `count`。**修复方法：** 只在诊断代码中检查闭包，并按位置配对 `function.__code__.co_freevars` 与 `function.__closure__`。生产逻辑应使用函数的公开调用接口，不应修改 cell 的内容。

## AI 时代

**生成代码在这里常犯的错**

生成的回调工厂经常把延迟绑定藏在 lambda 或嵌套的 `def` 中，在循环内创建函数时尤其如此。模型还可能机械地添加 `nonlocal`，即使代码只读取名称；或者用 `global` 取代它，悄悄改变状态所有权。另一种常见错误是在循环外只创建一个工厂结果，而每个使用方其实需要独立状态。

**让 AI 检查**

- 找出每个嵌套函数中的所有自由变量，并说明它们的绑定何时被读取。
- 跟踪循环中创建的回调，确认它们是共享一个 cell，还是分别绑定了本轮迭代的值。
- 验证每次 `nonlocal` 赋值都指向预期的外层函数调用，而不是模块状态。

**审查清单**

- 在循环结束后调用循环中创建的函数，并把结果与预期的逐轮值比较。
- 交错调用理应相互独立的闭包，检查状态是否在不同使用方之间泄漏。
- 检查长期存在的回调所保留的每个可变对象，确认其生命周期和所有权。

**提示词词汇**

使用准确术语：`closure`（闭包）、`free variable`（自由变量）、`enclosing scope`（外层作用域）、`late binding`（延迟绑定）、`cell`（cell 对象）、`nonlocal rebinding`（非局部重新绑定）、`bind by default argument`（通过默认参数绑定）。如果时机很重要，要求 AI 给出绑定与调用时间线；“解释这个 lambda”太含糊，无法暴露共享的 cell。

## CPython 如何存储 cell

CPython 使用<Term id="cell">cell 对象（cell object）</Term>实现捕获的绑定。cell 是一个小型容器，其中保存对捕获名称当前所绑定对象的引用。外层和内层代码把 cell 当作共享存储，而不是各自持有互不相关的局部槽位。因此，通过 `nonlocal` 重新绑定后，下一次调用闭包时能看到变化。这也说明了为什么“闭包复制了一个值”会造成误解。

### cell 变量与自由变量

对于嵌套函数生成的两个代码对象，同一个名称可以扮演不同角色。在 `make_counter` 中，`count` 是外层函数的局部名称，同时被内层函数引用。因此，外层代码把它当作 cell 变量。对于 `tick`，同一个名称则是由外层作用域提供的自由变量。

外层代码对象的 `co_cellvars` 标出需要 cell 的局部名称。内层代码对象的 `co_freevars` 标出必须从该代码对象外部取得 cell 的名称。这些属性描述的是编译时的名称分类。它们并不包含计数器在运行时不断变化的值。

### `__closure__` 与 cell 标识

函数对象的 `__closure__` 属性要么是 `None`，要么是一个 cell 元组。这些 cell 按位置对应 `function.__code__.co_freevars` 中的名称。对于 `tick`，`co_freevars` 中包含 `count`；每次调用后，对应 cell 的 `cell_contents` 都会变化。

同一次外层调用创建的两个函数，如果引用同一个外层绑定，就可以共享同一个 cell。不同外层调用创建的两个函数会得到不同的 cell，即使它们复用了同一个代码对象。这个标识差异正是前面两个计数器彼此独立的根源。

默认参数采用另一种方式解决循环陷阱。在 `lambda index=index: index` 中，绑定值作为函数默认值保存，而 `index` 是局部参数，不是自由变量。因此，这个 lambda 的参数不需要闭包 cell。

### `nonlocal` 改变了什么

函数运行前，编译器就会确定其中哪些名称属于局部、自由、cell 或全局名称。赋值通常会把目标名称归类为当前函数的局部名称。`nonlocal count` 会改变这项分类，让读取和写入都使用最近外层函数作用域中已经绑定 `count` 的 cell。

声明必须引用已有的外层函数绑定。它不能指向模块作用域，也不能创建新的外层绑定。找不到匹配的绑定时，Python 会在编译代码时抛出 `SyntaxError`。这种编译时分类也解释了为何不可达的赋值仍可能让前面的读取变成局部读取，并在该路径执行时触发 `UnboundLocalError`。

### `dis` 展示的内容

`dis` 模块会展示 CPython 生成的字节码指令。确切的指令序列取决于实现和版本，所以它适合解释特定运行时，不应当作可移植的 Python 契约。

在 CPython 3.14 中，外层计数器代码用 `MAKE_CELL` 创建捕获存储，并在构造内层函数的闭包元组时使用 `LOAD_CLOSURE`。内层代码以 `COPY_FREE_VARS` 开始，并通过解引用指令访问 `count`。`LOAD_DEREF` 读取 cell 所引用的对象。`count += 1` 算出新整数后，`STORE_DEREF` 会改变该 cell 引用的对象。普通局部变量指令使用的是快速局部槽位。

看到 `LOAD_DEREF`，而不是局部或全局加载指令，可以确认某个名称在该 CPython 构建中通过闭包存储解析。当生成代码包含多层嵌套作用域，源码又无法清楚表达所有权时，反汇编最有用。先查看 `co_freevars` 并应用源码层面的作用域规则；字节码只用于确认，不是应用接口。
